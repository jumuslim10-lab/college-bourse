# Мультиплощадочность: как это работает

**Статус: реализовано и покрыто тестами.** Раздел-справка для человека и для ИИ-агента.
Полное ТЗ проекта — [../../PROMPT.md](../../PROMPT.md); правила работы — [../../CLAUDE.md](../../CLAUDE.md).

## Что это

Один бот обслуживает несколько площадок (колледжей). Студент видит объявления только своей
площадки, но владелец в админке видит и модерирует всё.

## Как пользоваться

**Создать площадку (админ).** `/admin` → 🏫 Площадки → ➕ Создать площадку → код → название → город.
Код: латиница, цифры и дефис, 3–32 символа (`college-01`). Пробелы и заглавные нормализуются:
` College 01 ` → `college-01`. Бот сразу отдаёт инвайт-ссылку `https://t.me/<бот>?start=<код>`.

**Пригласить студентов.** Отправь инвайт-ссылку в чат площадки. Переход по ней привязывает
студента к площадке: `/start <код>` → площадка найдена → «✅ Ты на площадке …».

**Переключиться вручную.** Кнопка «🏢 Площадки» появляется в меню, только когда площадок больше
одной. Показывает список с количеством объявлений и отметкой текущей площадки. Пункт
«🌍 Все площадки» возвращает общий вид.

**Выключить площадку.** Нажатие на площадку в админке переключает `is_active`: она исчезает из
списка выбора и не принимает новых по инвайту, но данные и статистика сохраняются.

## Правила видимости (важно)

| Кто смотрит | Что видит |
|---|---|
| Площадка не выбрана (общий вид) | все объявления всех площадок |
| Выбрана площадка X | только объявления площадки X |
| Объявление без площадки (старое) | только в общем виде |
| Первая созданная площадка | забирает к себе весь общий пул: пользователей и объявления |
| Вторая и последующие площадки | никого не забирают, общий пул остаётся общим |

В коде это выражается так: у запросов каталога, поиска, счётчиков, статистики и рассылок есть
необязательный параметр `community_id`, а условие в SQL — `(? IS NULL OR community_id = ?)`.
Проверка видимости конкретного объявления — `services.can_view_community(user, listing)`;
сообщение при отказе — «Это объявление с другой площадкой».

## Что в коде

- `schema.sql` — таблица `communities`, поле `community_id` в `users` и `listings`,
  индексы `idx_listings_cat` (со `community_id`) и `idx_listings_community`;
- `bot/db.py` — методы площадок (`create_community`, `get_community_by_code`,
  `list_communities_with_counts`, `set_community_active`, `set_community_ambassador`,
  `adopt_unassigned`, `count_community_*`) и миграции, включая пересборку индекса;
- `bot/services.py` — `create_community`, `join_community`, `needs_community_switch`,
  `parse_start_payload`, `can_view_community`, `normalize_community_code`;
- `bot/handlers/communities.py` — «🏢 Площадки» и переключение;
- `bot/handlers/admin.py` — раздел «🏫 Площадки» (создание через FSM `CommunityForm`,
  включение/выключение, счётчики, инвайт-ссылка, статистика по площадкам);
- `bot/scheduler.py` — дайджест и рассылка считаются отдельно по каждой площадке;
- `tests/test_communities.py` — 14 тестов: коды, инвайты, изоляция каталога и поиска,
  статистика, забор пула, счётчики, индекс.

## Зачем это здесь, если Фаза 3

Мультиплощадочность — Фаза 3 по бизнес-плану: включать её в работу нужно только после того, как
первая площадка две недели держит ≥10 объявлений/день и ≥5 сделок/неделю. Код готов заранее, но
**вторая площадка не открывается без амбассадора** — иначе получится несколько пустых витрин
вместо одной живой.

## Чего ещё нет

- амбассадоры с долей выручки (поле `ambassador_user_id` в схеме есть, UI и учёта нет);
- отдельные админы на площадку (сейчас админы общие, из `ADMIN_IDS`);
- учёт выручки по площадкам (реклама пока учитывается общей рассылкой).
