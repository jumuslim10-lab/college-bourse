# CLAUDE.md — правила для ИИ-агента в этом проекте

Проект: Telegram-бот «Биржа колледжа» (Кыргызстан) — витрина объявлений «продаю/куплю» для одного
колледжа. Полное ТЗ и все принятые решения: **[PROMPT.md](PROMPT.md)** — читать перед любой задачей.
Краткий обзор и быстрый старт: [README.md](README.md).

## Жёсткие запреты (не обсуждать и не реализовывать)

- **Никакого приёма денег в боте**: ни эквайринга, ни Telegram Stars, ни «безопасной сделки»,
  ни эскроу, ни роли «гаранта». Чужие деньги через бота не проходят вообще.
- **Никакой комиссии с оборота** и процента со сделки — даже с крупной.
- **Нельзя ухудшать бесплатный тариф** (3 объявления, каталог, поиск, отзывы, раскрытие контакта).
- **Нельзя рекламировать** услуги «сделаю контрольную/курсовую/диплом».
- Нельзя разрешать домашнюю еду как категорию: только фабричная упаковка или партнёрская доставка.
- Нельзя менять порядок монетизации: подписка включается только после гейта
  «продавец с 5+ закрытыми сделками», и первым делом — статистика продавца, а не тарифы.

## Обязательные проверки перед завершением задачи

```powershell
# если .venv ещё нет:
# python -m venv .venv; .venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest -q      # 49 тестов должны остаться зелёными
.venv\Scripts\python.exe -m ruff check .   # линтер должен остаться чистым
```

Новая логика сопровождается тестом в `tests/`. Не коммитить `.env`, `data/`, `.venv`, кэши.

## Инварианты кода

- Все пользовательские тексты — только в `bot/texts.py`; валюта — константа `CURRENCY = "сом"`.
- Разделы, TTL и правило видимости — в `bot/categories.py`.
- Бизнес-логика публикации, модерации, топа, дайджеста — в `bot/services.py`, не в хендлерах.
- Все SQL-запросы — в `bot/db.py`; в хендлерах SQL писать нельзя.
- SQL обязан быть диалект-нейтральным: проект работает и на SQLite, и на Postgres (Supabase).
  Нельзя `INSERT OR IGNORE`, `AUTOINCREMENT`, `PRAGMA ...(` , `sqlite_master`, `lastrowid`,
  `cursor.rowcount`, `executescript` — вместо них `ON CONFLICT DO NOTHING`, `RETURNING id`
  и методы бэкенда. Диалектный код живёт только в `bot/storage.py`. Эти запреты проверяет
  `tests/test_storage.py::test_repository_sql_stays_dialect_neutral`.
- Схема правится в **двух** файлах: `schema.sql` и `schema_postgres.sql`. Наборы таблиц и колонок
  обязаны совпадать (проверяет `test_both_schemas_define_same_tables_and_columns`).
- Изменения схемы: `schema.sql` + догоняющая миграция в `Database.migrate()` (через
  `PRAGMA table_info`/`information_schema` — метод `backend.column_names`), чтобы существующая
  база обновлялась сама.
- Формат callback-данных и FSM-состояния не выдумывать: они перечислены в `PROMPT.md`, раздел 8.
- Площадки: фильтр по площадке — необязательный параметр `community_id` в запросах
  (`None` = общий вид, видно всё). Новые запросы к `listings`, которые видит студент, обязаны
  поддерживать этот фильтр, иначе объявления потекут между колледжами. Видимость внутри бота
  проверяется через `services.can_view_community`.
- Хендлеры получают `user`, `db`, `config` из мидлварей/workflow data — новых зависимостей
  в сигнатуры не добавлять без нужды.
- Экономия обращений к базе (важно при облачной базе, где запрос стоит ~0,9 с):
  `UserMiddleware` кеширует строку пользователя на 60 с — повторные нажатия не ходят в базу;
  экран раздела берётся одним запросом через `list_active(..., with_total=True)`
  (`COUNT(*) OVER ()`). Не добавляй запросы «на всякий случай» и не ломай эти два места.

## Когда задача неясна

- Решения, которые меняют **бизнес-модель, монетизацию или правила биржи**, агент не принимает
  сам: спрашивает владельца проекта.
- Технические детали (имена, структура, тесты, рефакторинг) — на усмотрение агента,
  но в рамках инвариантов выше.

## Текущее состояние

- **Фаза 1 (бот) реализована**: каталог по разделам с поиском, публикация с лимитами и автофильтром,
  ручная модерация, сделки с подтверждением, отзывы, жалобы, топ на 24 часа, авто-архив (1/7/14 дней),
  реклама партнёров, рассылка, ежедневный дайджест, админка со статистикой, баны.
- **Мультиплощадочность реализована** (7 роутеров, `bot/handlers/communities.py`): таблица
  `communities`, инвайт-ссылки `?start=<код>`, кнопка «🏢 Площадки», общий вид «🌍 Все площадки»,
  фильтрация каталога/поиска/статистики/рассылок по площадке, админка площадок, первая площадка
  забирает общий пул.
- **Хранилище переключаемое**: сейчас бот работает **на облаке** (`DB_BACKEND=postgres`, проект
  Supabase `mortsrfmloviqvgjbmvr`, регион Singapore). Локальный режим — `DB_BACKEND=sqlite`,
  данные в `data/bot.db`. Драйверы — `bot/storage.py`, схемы — `schema.sql` и `schema_postgres.sql`.
  Тесты гоняются на обеих базах; на облачной — через `TEST_DATABASE_URL`.
- **Экономия запросов к облаку**: кеш пользователя в `UserMiddleware` (60 с) и экран раздела
  одним запросом. При ~0,9 с на запрос это разница между «терпимо» и «висит».
- **Следующий шаг по инфраструктуре**: VPS в Сингапуре (там же, где база) — тогда запросы станут
  1–5 мс вместо ~900. Всё для развёртывания готово в `deploy/`.
- Логи фонового запуска бота — в `logs/bot.err.log` (каталог в `.gitignore`).
- **Не реализовано (ждёт гейтов)**: статистика продавца, подписка «Продавец+», платное размещение
  объявлений от 5 000 сом, амбассадоры с долей выручки, отдельные админы на площадку.
  Спецификации — `PROMPT.md`, раздел 16.
- **Бизнес-состояние**: Фаза 0 (проверка руками в чате колледжа) ещё не пройдена. Гейт для движения
  дальше: ≥10 объявлений в день и ≥5 сделок в неделю две недели подряд. Вторая площадка
  открывается только после этого гейта и только вместе с амбассадором.
